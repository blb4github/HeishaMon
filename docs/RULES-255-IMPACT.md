# Rules VM: 127 → 255 variable slots — benefits, cost and validation

**Status:** development proposal / impact analysis, not an upstream release.  
**Implementation:** [HeishaMon fork draft PR #5](https://github.com/blb4github/HeishaMon/pull/5), branch `feature/rules-255-variable-slots`.  
**Target upstreams:** [CurlyMoo/rules](https://github.com/CurlyMoo/rules) first (generic Rules engine), then [heishamon/HeishaMon](https://github.com/heishamon/HeishaMon) for the embedded copy / integration. This mirrors [CurlyMoo/rules PR #18](https://github.com/CurlyMoo/rules/pull/18) and [HeishaMon PR #1050](https://github.com/heishamon/HeishaMon/pull/1050).

## Problem and value

The existing bytecode instruction is four bytes: a `uint8_t` opcode and three signed `int8_t` operands. Index values 128–255 cannot be represented as positive signed 8-bit operands: they become negative and can be confused with temporary/heap references. Merely relaxing the compiler's 127-slot limit is unsafe.

A real ESP32-S3 HeishaMon installation now uses **138 slots** with 16 Rules blocks. The former 127-slot ceiling forced users to avoid further variables and compromises Rules readability/maintainability. A 255-slot ceiling provides additional headroom without changing user-facing Rules syntax, the meaning of variables, or the 24-bit Rules integer representation.

## Implementation being tested

- Widen the three `vm_top_t` operands to signed `int16_t`. The bytecode instruction becomes **8 bytes** because of layout/alignment (enforced with `static_assert`).
- Widen relevant compiler, optimizer and VM index/operand handling, retaining negative references and signed comparisons.
- Apply an explicit **255-slot maximum**; reject 256 in the compiler.
- Do **not** preallocate a 255-entry variable table merely because the upper bound is raised.
- No user-visible Rules syntax changes and no modifications to heat-pump control logic.

**Important:** this is a bytecode *format/ABI change*, not a backwards-compatible encoding of existing bytecode. Generated bytecode should be rebuilt from Rules source under the matching engine. Do not assume old/new cached or persisted bytecode can be exchanged.

## Quantified memory cost

### Every bytecode instruction grows — not only those above slot 127

| Property | Original | Proposed | Change |
|---|---:|---:|---:|
| `vm_top_t` size | 4 bytes | 8 bytes | **+100%** |
| Maximum named-variable slots | 127 | 255 | +128 |
| Per-variable slot (`vm_vchar_t`) | 8 bytes | 8 bytes | unchanged |
| Additional variable-table storage *if all 128 newly available slots are used* | — | 1,024 bytes | allocated according to actual usage, not upfront |

### Real installation: 2026-11-16 `HeishaMon_20261116.log`

- Hardware: HeishaMon Large, ESP32-S3-MINI-1-N4R2 (4 MB flash, 2 MB PSRAM), Ethernet and OpenTherm enabled.
- Firmware: `Alpha-da6832a`; tested Rules `2611.09` and `2611.10`, 16 blocks.
- **138/255 slots used**, variable-stack data **1,104 bytes** (138 × 8).
- The individual compiled bytecode sizes from all 16 Rules blocks sum to **11,976 bytes**, or **1,497 instructions** of 8 bytes each.
- The *identical sequence of 1,497 instructions* encoded as 4-byte instructions would occupy **5,988 bytes**. Thus the encoding change itself costs **+5,988 bytes** for this specific Rules program. This is a mathematical like-for-like comparison, **not** a measured successful run of this >127-slot program on the old engine (which would reject it).
- Reported Rules mempool use: **17,268 / 32,768 bytes** (**52.7%**); free space within that pool: **15,500 bytes** (**47.3%**).
- Reported system free heap during the capture: usually ~164.7 KB; free PSRAM ~2,052,088 bytes. No sustained downward memory trend was observed in that capture.

**Accounting caveat:** on ESP32 the Rules mempool is a preallocated 32 KiB region (allocated via `ps_malloc`). Increasing the bytes consumed *inside* that pool does not necessarily reduce the general free-heap/PSRAM counters by the same number once the pool has already been allocated. The practical direct cost is less space for compiled Rules within the fixed pool and therefore a greater risk of exhausting it for complex Rules programs.

### Smaller platforms

In HeishaMon, `MEMPOOL_SIZE` is `32*1024` on ESP32. The ESP8266 configuration derives its Rules mempool size from `MMU_SEC_HEAP_SIZE`, or falls back to `4096` bytes if that macro is unavailable. The **same doubling of instruction storage** may therefore be materially more restrictive on ESP8266.

ESP8266 firmware **compilation** succeeded; equivalent **on-device memory and Rules execution tests have not been performed**. A pass on ESP32-S3 must not be represented as ESP8266 performance or capacity validation.

## Other disadvantages and trade-offs

1. **Reduced Rules capacity for a fixed mempool:** the doubled bytecode footprint may prevent some Rules programs that previously fit from compiling, even when they use fewer than 128 slots.
2. **Wider change surface:** parser/compiler, optimizer, operand interpretation, VM execution, offsets and diagnostic code must consistently handle signed 16-bit operands. An isolated change to the variable-count check is insufficient.
3. **Bytecode incompatibility:** old and new instruction layouts are different. Only Rules source is intended to be portable across firmware builds, subject to slot limits.
4. **Potential code-size / execution-time impact:** wider operands and extra conversions can affect machine code size, cache behavior and execution speed. **No controlled baseline comparison has yet established the magnitude**. No claims of zero slowdown or unchanged flash consumption should be made.
5. **Cross-platform risk:** ESP8266 has a smaller memory budget and different memory behavior; real-device testing is necessary before recommending the change for all hardware.
6. **Limits remain:** this proposal only raises the named-variable slot ceiling. It does not make the Rules mempool, execution stack, timer count, expression complexity or unrelated operand limits unlimited.

### Alternative implementation

A compact extension/prefix encoding could preserve the existing four-byte instruction format for common references and encode high indices only where needed. That could save significant memory for scripts below 128 slots, but would add complexity to code generation, jump offsets, optimization and VM decoding. The current prototype deliberately trades **memory for simpler, uniformly signed operands**. The upstream maintainer should assess whether that trade-off is acceptable; no compact alternative has yet been benchmarked.

## Acceptance criteria before upstream submission

- Verify a normal heating cycle on the current production ESP32-S3 installation (especially the morning warm-up), including compressor state changes, TaShift/PI and GPIO33 output states.
- Confirm no new Rules exceptions, repeated reboots, communication problems or progressive memory degradation.
- Run bytecode regression cases with mixed positive high indices and negative heap/temporary references, and retain the 255/256 boundary tests.
- Inspect the complete bytecode index/sign handling for overlooked truncation or overflow paths; verify the effect on the Rules mempool and ESP8266 support.
- Preferably compare against an otherwise identical baseline build for flash size, compile time, execution time and mempool usage.
- Keep changes to the Rules engine independent of the experimental async webserver work.
- After successful review, propose the library change to **CurlyMoo/rules** first, then integrate the accepted version into **heishamon/HeishaMon** (Igor/repository maintainers).
