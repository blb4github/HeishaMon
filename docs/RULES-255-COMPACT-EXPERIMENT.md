# Experimental compact Rules VM: 255 variable slots, 4-byte instructions

**Status:** host-validated experiment; **not approved for flashing**, not merged, and not yet proposed upstream.  
**Branch:** [`experiment/rules-255-compact-bytecode`](https://github.com/blb4github/HeishaMon/tree/experiment/rules-255-compact-bytecode).  
**Comparison:** [draft PR #5](https://github.com/blb4github/HeishaMon/pull/5) retains the earlier 8-byte instruction version.

## Why this experiment exists

The first working 255-slot extension widened three signed 8-bit instruction operands to signed 16-bit fields, growing each bytecode instruction from **4 to 8 bytes**. This incurs a 100% instruction-storage penalty on *every* Rules program, even when it uses fewer than 128 variable slots. This is undesirable for the smaller ESP8266 Rules pool, and wastes Rules mempool space on ESP32.

The alternative keeps `vm_top_t` as the original **4-byte** layout:

```cpp
typedef struct vm_top_t {
  uint8_t type;
  int8_t a, b, c;
} __attribute__((aligned(4))) vm_top_t;
static_assert(sizeof(vm_top_t) == 4, "Rules bytecode instruction must occupy 4 bytes");
```

An 8-bit byte can encode indices 0–255; the difficulty is **operand meaning**, not bit capacity. The VM uses negative signed operands for heap/temporary references and positive/unsigned operands for named variables. Therefore mixed meanings must be disambiguated explicitly.

## Changes versus the 8-byte prototype

1. Restore `vm_top_t.a/b/c` to one byte each and assert the 4-byte instruction size.
2. Interpret variable-index fields as **unsigned** when the opcode unambiguously identifies a named variable (notably `OP_GETVAL.b`, `OP_SETVAL.a`, `OP_CALL.b`).
3. For ambiguous operands, reuse the existing `c` flag semantics:
   - `OP_SETVAL` with a positive source index greater than `INT8_MAX`: mark `c=2` to distinguish the source from a negative heap reference.
   - `OP_PUSH` with a positive high index: mark `c=1` to identify a variable source rather than a negative heap reference.
4. Preserve signed extension of negative operand bytes explicitly with `(int8_t)getval(...)`. This also matters for the ESP8266 MMU shim, which reads bytes through unsigned accessors.
5. **Fix the optimizer's statement splitting**: it previously interpreted `OP_SETVAL.a` (a named-variable destination) as a signed index. When that destination was 128 or higher, it split the statement *before* the assignment, so temporary references were not correctly resolved. `OP_SETVAL.a` must be excluded from the negative-temporary-reference test.

There are **no extra opcodes** in this prototype, and no user-visible Rules syntax change.

### Explicit constraints / remaining risks

- An 8-bit negative reference can still only represent its existing negative-operand range; raising named-variable slots does not independently extend heap/temporary offsets, nested expressions or the Rules mempool. Verify those constraints independently.
- The `c` flag meanings are opcode-dependent and require thorough test coverage and upstream review; this is not a general-purpose larger integer encoding.
- Host regression tests do not establish real-device safety, performance, or ESP8266 runtime behavior.
- Persisted/generated bytecode compatibility must be reviewed before integrating upstream; the source Rules remain the intended interchange format.
- This branch has intentionally not combined CurlyMoo's experimental asynchronous webserver code.

## Initial measured comparison

Both measurements use the **same existing 16-block HeishaMon Rules reference** and the host harness. The test workflow checks out `HeishaMon-Rules-with-Opentherm-Thermostat/main`; for a fully reproducible upstream benchmark pin the reference to a specific commit.

| Metric | 8-byte version, Rules VM check | Compact 4-byte version, Rules VM check |
|---|---:|---:|
| Bytecode instruction size | 8 bytes | **4 bytes** |
| Rules mempool used, current reference | **17,332 / 49,152 bytes** | **11,984 / 49,152 bytes** |
| Difference | — | **−5,348 bytes (−30.9% of the used pool)** |
| Host regressions | 48 passed | **48 passed** |
| Slot count 127, 128, 200, 255 | Pass | **Pass** |
| 256 slots | Rejected | **Rejected** |
| Real Rules reference, 16 blocks | PARSE OK | **PARSE OK** |

CI evidence:

- 8-byte version: [Rules VM check](https://github.com/blb4github/HeishaMon/actions/runs/43718367517)
- Compact version with extended boundary scenarios: [Rules VM check](https://github.com/blb4github/HeishaMon/actions/runs/43785768863)

The compact boundary scenario additionally checks **high-index-to-low-index assignments** and **high-index variables passed as function arguments**, not only reading/comparing the final variable slot.

The saving in the host mempool is significant but **is not the same as a 5,348-byte measured saving in overall ESP32 free heap or PSRAM**.
